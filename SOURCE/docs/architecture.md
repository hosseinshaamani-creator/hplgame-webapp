# HPLGAME — معماری و دادهٔ فاز ۱، هفتهٔ سوم

تاریخ: ۳۰ اکتبر ۲۰۲۶. این سند ردیف هفتهٔ ۳ رودمپ (۱۵ تا ۲۱ آبان ۱۴۰۳ در برنامهٔ تاریخی) را پوشش می‌دهد. مخزن، CI و رابط هفته‌های ۱ و ۲ مبنا هستند؛ مصاحبه‌های واقعی، تصویب KPIها و ارزیابی آموزشی هنوز شواهد نهایی ندارند.

## معماری اجراشده

مرورگر ← `index.html` و فایل‌های محلی ← `app.js` (پوسته، مسیرهای hash، تم، ورود واقعی قبلی) ← ماژول‌های مستقل `discovery.js` و `prototype.js`.

`discovery.js` ورودی و مسیر پنج‌قدم هفته‌های قبل را نگه می‌دارد. `prototype.js` فقط زیرمسیر `#/studio/*` را مدیریت می‌کند: ورود/ثبت‌نام آزمایشی، سه درس همراه چت، canvas و پنجرهٔ اشتراک. استایل افزودهٔ `prototype.css` از متغیرهای رنگ و فونت موجود استفاده می‌کند. باندل با esbuild ساخته و با GitHub Actions روی Pages منتشر می‌شود. نام فایل‌های ورودی خروجی با hash محتوا نسخه می‌گیرد. مسیرهای نسبی با `/hplgame-webapp/` سازگارند.

در این تحویل سرور، سرویس AI یا پرداخت جدید وجود ندارد. حساب واقعی نسخهٔ قبل از `backend.js` و migrationهای `supabase/migrations` استفاده می‌کند؛ پیکربندی عمومی فعلی برای فعال کردن آن کافی نیست. پروفایل آزمایشی هرگز به عنوان session احراز هویت واقعی به آن ماژول داده نمی‌شود.

## وایرفریم و ماشین وضعیت

| صفحه | ناحیهٔ اصلی | اقدام و مقصد |
|---|---|---|
| خانه | هیرو و ایدهٔ هفتهٔ ۲، پیشنهادها و سطح | شروع مسیر → `#/idea`؛ کارت جدید → `#/studio/login` |
| مسیر ایده | خلاصه و پنج درس قبلی | ادامه در کارگاه آزمایشی → ورود آزمایشی |
| ورود/ثبت‌نام نمونه | کارت نام مستعار و توضیح محلی بودن | تغییر بین login/signup؛ نام معتبر → ساخت اولین نمونه از ایدهٔ ذخیره‌شده |
| مربی | دو ستون درس/پیشرفت و چت هوپی | پاسخ غلط → بازخورد و تلاش مجدد؛ درست → درس بعد؛ تب بوم → preview |
| بوم | بازی در canvas، پیام وضعیت و جهت‌ها | اجرا، حرکت، برد واقعی پس از سه برخورد، شروع مجدد |
| بازی‌های من | کارت همان بازی اول و وضعیت | ادامهٔ بازی اول؛ ساخت دوم → paywall؛ خروجی JSON یا حذف با تأیید |
| قفل اشتراک | modal با توضیح مدل فری‌میوم | وضعیت اشتراک → پیام غیرفعال بودن پرداخت؛ ادامهٔ رایگان/Escape → بستن |

قفل دوم صرفاً تغییر `modal` است و Game جدید ایجاد نمی‌کند. ارسال دوبارهٔ نام آزمایشی بازی اول را حفظ می‌کند؛ تغییر ایدهٔ لندینگ بازی ذخیره‌شدهٔ نمونه را بازنویسی نمی‌کند. تب‌ها hash واقعی دارند و back/forward و بازخوانی کار می‌کنند. ورود مستقیم به preview بدون پروفایل آزمایشی، فرم ورود نشان می‌دهد. بدون ایدهٔ معتبر، کاربر به خانه راهنمایی می‌شود. canvas حرکت را فقط پس از «اجرا» می‌پذیرد؛ پیشرفت درس و برد نمونه دو وضعیت مستقل‌اند.

## مدل محلی فعلی

| مدل | فیلدها و محدودیت | رابطه/مالکیت |
|---|---|---|
| DemoUser | `name`: نام مستعار ۲ تا ۴۰ نویسه؛ بدون رمز و ایمیل | یک پروفایل روی این مرورگر؛ هویت معتبر نیست |
| DemoGame | `id`: UUID، `idea`: حداکثر ۶۰۰، `step`: عدد صحیح ۰..۳، `won`: boolean، `messages`: حداکثر ۳۰ | حداکثر یک نمونه در storage مشترک این مرورگر |
| DemoMessage | `role`: user/coach، `text`: حداکثر ۵۰۰ | متعلق به همان Game؛ متن برای DOM escape می‌شود |
| Lesson | سه تعریف ثابت شامل عنوان، محتوا، سؤال، گزینه‌ها و پاسخ صحیح | `step` شمار درس‌های درست است؛ پاسخ خام ذخیره نمی‌شود |
| BoardSession | مختصات x/y، مجموعهٔ سه ستاره، running | فقط حافظه؛ با بازخوانی/تغییر تب از ابتدا؛ فقط won پایدار است |

کلید `hplgame-prototype-v1` شامل `{user, game, updatedAt}` است. خواندن، شکل داده و زمان و طول متن را بررسی می‌کند؛ مقدار خراب یا قدیمی به حالت خالی برمی‌گردد. LocalStorage قابل ویرایش است؛ این بررسی مرز امنیتی یا ضدتقلب نیست. پروفایل مشترک دستگاه است و خروج آزمایشی فقط user را خالی می‌کند؛ Game برای ادامه در همان دستگاه می‌ماند. اسم جدید مالک جدیدِ داده ایجاد نمی‌کند؛ برای تفکیک واقعی کاربران باید حساب سروری فعال شود.

## طرح مدل محصول سروری — اجرا نشده در این هفته

| موجودیت | کلیدها و فیلدهای پیشنهادی | قواعد |
|---|---|---|
| User | `id` UUID از Auth، `display_name`، `created_at`، `deleted_at` | رمز فقط در سرویس Auth؛ نقش و اشتراک از کلاینت پذیرفته نشوند |
| Game | `id`، `owner_id → User.id`، `idea`، `template_id`، `status`، `created_at/updated_at`، `version` | سقف متن و نسخه‌بندی؛ شمارش بازی و سهمیه در تراکنش سروری |
| Step | `id`، `game_id`، `position`، `title`، `goal`، `status`، `completed_at` | یکتایی `(game_id,position)` و ترتیب معتبر؛ اعتبارسنجی تکمیل |
| Message | `id`، `game_id`، `step_id` nullable، `role`، `content`، `created_at` | فقط مالک بازی؛ سقف متن/تعداد؛ role مربی توسط سرور تعیین شود |
| Entitlement | `user_id`، `plan`، `status`، `expires_at`، `payment_event_id` | فقط webhook معتبر و امضاشده حق تغییر دارد؛ idempotency الزامی |

این‌ها قرارداد پیشنهادی آینده‌اند، نه migration جدید. پروژهٔ Supabase قبلی جداول خودش را دارد؛ اضافه کردن Game/Message/Step نیازمند migration، مهاجرت داده و آزمون RLS جداگانه است. `DemoGame` نباید خودکار به حساب واقعی منتقل شود؛ انتقال باید با رضایت و اعتبارسنجی سروری انجام شود.

## جریان دسترسی و مرز اعتماد

- صفحات عمومی و نمونه بدون اطلاعات محرمانه قابل باز شدن‌اند. نمایش فرم آزمایشی احراز هویت نیست؛ هر شخص روی همان دستگاه می‌تواند دادهٔ نمونه را ببیند. نام مستعار و ایدهٔ غیرحساس استفاده شود.
- مسیرهای محافظت‌شدهٔ قبلی همچنان به حساب واقعی نیاز دارند. کلید و state آزمایشی به session واقعی یا امتیاز کارگاه تبدیل نمی‌شود.
- در معماری آینده: session معتبر → بررسی مالکیت `owner_id = auth.uid()` در RLS → بررسی سهمیهٔ بازی اول/اشتراک روی سرور → ساخت بازی در تراکنش. قفل UI به تنهایی دسترسی پولی را امن نمی‌کند.
- API Key مدل زبانی و کلید service-role فقط در سرور/secret store؛ هرگز در JS عمومی یا LocalStorage. در این تحویل هیچ کلید جدید یا جعلی اضافه نشده است. build قبلی همچنان کلید secret و service-role را رد می‌کند.
- ایده و چت به HTML اجرایی تبدیل نمی‌شوند؛ canvas کد ثابت است، `eval` و اجرای کد دلخواه ندارد. CSP موجود و مسیرهای محلی حفظ می‌شوند. پاسخ مربی محلی است و هیچ داده‌ای به ارائه‌دهندهٔ AI ارسال نمی‌کند.
- پنجرهٔ modal عنوان دسترس‌پذیر، فوکوس اولیه، محدود کردن Tab، Escape و بازگشت فوکوس دارد. نواحی پشت modal موقتاً inert می‌شوند.

## نگهداری و حذف داده

| دسته | سیاست این نسخه |
|---|---|
| پروفایل/بازی/چت نمونه | حداکثر ۳۰ روز از آخرین ذخیره؛ در بارگذاری بعد از انقضا از state خوانده نمی‌شود و slot محلی پاک می‌شود؛ پیام‌ها حداکثر ۳۰ مورد |
| وضعیت موقت بوم | فقط حافظه؛ بازخوانی یا خروج از تب داخلی آن را از نو می‌سازد |
| خروج آزمایشی | نام پروفایل پاک، بازی برای بازگشت همان دستگاه باقی؛ خروج برابر حذف نیست |
| حذف نمونه | از بازی‌های من، با modal تأیید؛ فقط کلید نمونه حذف می‌شود؛ ایده و پژوهش هفته‌های قبل باقی می‌ماند |
| خروجی JSON | فقط با کلیک کاربر؛ نام کاربر صادر نمی‌شود؛ مدیریت فایل دانلودی با کاربر است |
| هفته‌های ۱ و ۲ | سیاست فعلی محلی بدون TTL خودکار تغییر نکرده؛ پاک کردن site data مرورگر آن را حذف می‌کند؛ نمونه این کلیدها را پاک نمی‌کند |
| دادهٔ سروری آینده | پیشنهاد: حذف حساب → قطع دسترسی فوری، پاک‌سازی دادهٔ فعال تا ۳۰ روز، انقضای backup تا ۹۰ روز؛ نیازمند تصویب و پیاده‌سازی، اکنون تضمین عملیاتی نیست |

زمان‌بندی پس‌زمینه وجود ندارد؛ TTL در بارگذاری بعدی اعمال می‌شود. زمان کلاینت قابل اعتماد امنیتی نیست. حالت محدودیت storage با پیام واضح در حافظه ادامه می‌یابد؛ اطلاعات با reload از دست می‌رود. جمع‌آوری مرکزی KPI و نگهداری log شخصی در این هفته اضافه نشده است.
