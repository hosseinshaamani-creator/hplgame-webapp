# معماری و مدل دادهٔ HPLGAME — هفتهٔ سوم، نسخهٔ اصلاح‌شده

تاریخ: ۳۰ اکتبر ۲۰۲۶. این سند رفتار پیاده‌سازی‌شده را از طرح سروری آینده جدا می‌کند.

## معماری فعلی

GitHub Pages فایل‌های ایستای esbuild را از `SOURCE/dist` منتشر می‌کند. `app.js` پوسته، hash routing و اتصال ماژول‌ها را دارد. `discovery.js` ورودی ایده، پیشنهادها، پژوهش و تم را حفظ می‌کند؛ callback ثبت ایده مستقیماً `submitPrototypeIdea` را صدا می‌زند. `prototype.js` ورود محلی، مربی، پروژه‌ها، بوم و اشتراک آزمایشی را مدیریت می‌کند. `prototype.css` از رنگ‌ها و فونت موجود استفاده می‌کند.

هیچ سرور، درخواست AI، پرداخت یا کلید جدیدی اضافه نشده است. Auth قبلی Supabase مستقل باقی است: اگر backend پیکربندی شده باشد، مسیرهای محافظت‌شده همان Auth و RLS قبلی را دارند. در نسخهٔ ایستای بدون backend، لینک‌های حساب، بازی‌ها، آموزش و راهنما به کارگاه آزمایشی هدایت می‌شوند؛ session محلی هرگز session سروری محسوب نمی‌شود.

## جریان و وضعیت

| ورودی | رفتار |
|---|---|
| ورود به کارگاه یا دکمه‌های هدر | مودال با تب ورود/ثبت‌نام، ایمیل، رمز و اعتبارسنجی؛ ثبت‌نام نام و تکرار رمز هم دارد |
| ثبت‌نام موفق | ساخت حساب محلی و ورود فوری؛ نام و وضعیت در هدر و سایدبار؛ بازی مهمان به همان حساب منتقل می‌شود |
| ورود مجدد | بررسی ایمیل و verifier رمز، بازیابی فقط پروژه‌های همان حساب |
| شروع مسیر یا پیشنهاد سریع | ذخیرهٔ ایده و ورود مستقیم به مربی؛ پیام اول کاربر همان ایده است؛ ثبت‌نام برای بازی اول اجباری نیست |
| ثبت دوبارهٔ ایدهٔ عیناً یکسان | ادامهٔ پروژهٔ موجود، بدون مصرف سهمیه |
| بازی دوم برای کاربر رایگان | باز شدن paywall بدون ساخت یا بازنویسی پروژه |
| فعال‌کردن پرمیوم آزمایشی | پس از ورود، باز شدن چندپروژه‌ای محلی؛ ایدهٔ در انتظار ساخته می‌شود یا فرم بازی جدید باز می‌شود |
| مربی | سه گام، پاسخ‌های متناسب با نوع بازی و سؤال؛ دکمه‌های گام بعد، کد و سؤال؛ متن کاربر اجرا نمی‌شود |
| بوم کنار مربی | دوز دو بازیکن با کلیک و برد/مساوی؛ مار با غذا، رشد و برخورد؛ فلپی آموزشی روی شبکه با بال‌زدن، موانع و خط پایان؛ ایده‌های دیگر نمونهٔ سه ستاره |
| خروج | session محلی خالی می‌شود؛ پروژه‌های حساب محفوظ و از نمای مهمان خارج‌اند |

درخواست بازی جدید همه از یک تابع سهمیه عبور می‌کنند، از جمله ورود از لندینگ. بدون پرمیوم فقط یک بازی برای حساب یا مهمان ساخته می‌شود. سقف نمونهٔ پرمیوم ۲۰ بازی و سقف حساب‌های محلی ۲۰ عدد است. رفت‌وبرگشت تب‌های داخلی و ارسال چت، وضعیت بوم را در حافظه حفظ می‌کنند؛ reload بوم را ریست می‌کند. `step` و `won` مستقل‌اند؛ «اجرا» یا اتمام درس، برد بازی ثبت نمی‌کند.

## مدل‌های محلی اجراشده

کلید `hplgame-prototype-v1` اکنون `{accounts, sessionId, guestGames, activeId, updatedAt}` دارد. قالب قدیمی `{user,game}` بدون حذف بازی به پروژهٔ مهمان مهاجرت می‌کند؛ نام مستعار قدیمی بدون ایمیل/رمز به عنوان حساب تأیید نمی‌شود.

| مدل | فیلدها و رابطه |
|---|---|
| DemoUser | `id` UUID، `name` بین ۲ تا ۴۰، `email` معتبر حداکثر ۲۵۴، `salt`، `verifier`، `premium` آزمایشی، `games[]` |
| DemoGame | `id` UUID، `idea` بین ۲ تا ۶۰۰، `step` صفر تا سه، `won`، `messages[]`؛ متعلق به حساب یا سبد مهمان |
| DemoMessage | `role` user/coach، `text` حداکثر ۳۰۰۰؛ آخرین ۴۰ پیام هر بازی؛ ورودی چت کاربر حداکثر ۵۰۰ |
| Step | سه تعریف ثابت متناسب با tic/snake/flappy/stars؛ محتوای آموزشی و نمونه‌کد ثابت، پیشرفت در `game.step` |
| BoardSession | Map حافظه با کلید game.id؛ مختصات، running/ended، وضعیت مار/غذا یا خانه‌های دوز، نوبت و پیام وضعیت |

رمز خام ذخیره نمی‌شود: Web Crypto با PBKDF2/SHA-256، salt تصادفی ۱۶ بایت، ۱۰۰۰۰۰ تکرار و خروجی ۲۵۶ بیت یک verifier می‌سازد. ایمیل تأیید نمی‌شود. ورود محلی برای شبیه‌سازی UX است؛ LocalStorage و پرچم premium توسط صاحب دستگاه قابل تغییرند و هیچ مرز امنیتی تولیدی یا پرداختی ایجاد نمی‌کنند. از رمز مخصوص تست استفاده شود. بازنشانی رمز/ارسال ایمیل در این محدوده وجود ندارد.

## دسترسی، اعتبارسنجی و نگهداری

- خواندن دادهٔ محلی، شکل داده، طول متن، نقش پیام، بازهٔ step و زمان را اعتبارسنجی می‌کند. JSON خراب یا انقضا صفحه را نمی‌شکند.
- TTL برابر ۳۰ روز از آخرین ذخیره است. پاک‌سازی در بارگذاری بعدی انجام می‌شود؛ worker زمان‌بندی‌شده وجود ندارد. تغییر ساعت دستگاه قابل اعتماد امنیتی نیست.
- حساب‌های آزمایشی پروژه‌های جدا دارند. با این حال دادهٔ تمام حساب‌های یک دستگاه در همان LocalStorage قابل مشاهده است؛ اطلاعات حساس وارد نشود.
- خروج، حذف نیست. «پاک کردن دادهٔ پروتوتایپ» با تأیید تمام حساب‌ها و بازی‌های آزمایشی را پاک می‌کند و کلید ایده/پژوهش هفته‌های ۱ و ۲ را حفظ می‌کند.
- خروجی JSON فقط games حساب فعال/مهمان را دارد؛ نام، ایمیل، salt و verifier صادر نمی‌شوند. فایل دانلودشده تحت مدیریت کاربر است.
- storage مسدود یا پر، با پیام مشخص در حافظه ادامه می‌دهد؛ reload دادهٔ ذخیره‌نشده را از بین می‌برد.
- ایده و پیام با escapeHTML نمایش داده می‌شوند. بوم فقط منطق ثابت دارد؛ `eval`، اجرای کد ورودی، API Key جعلی یا secret جدید وجود ندارد. CSP و کنترل build علیه service-role حفظ شده‌اند.
- مودال‌ها عنوان، فوکوس اولیه، Tab trap، Escape، بازگشت فوکوس و inert کردن محتوای پشت پنجره دارند.
- پالت، RTL، Vazirmatn، هوپی و ذخیرهٔ تم دست‌نخورده‌اند. دادهٔ پژوهش و ایدهٔ قدیمی همچنان سیاست محلی قبلی بدون TTL خودکار دارند.

## قرارداد پیشنهادی سرور — اجرا نشده

| موجودیت | کلیدها و قواعد |
|---|---|
| User | `id` از Auth، display_name، created_at، deleted_at؛ رمز تنها در سرویس Auth |
| Game | `id`، `owner_id → User.id`، idea، template_id، status، version و timestamps؛ RLS مالکیت |
| Step | `id`، `game_id`، position، title، goal، status، completed_at؛ یکتایی game/position |
| Message | `id`، `game_id`، `step_id` اختیاری، role، content، created_at؛ پیام مربی فقط از سرور |
| Entitlement | user_id، plan، status، expires_at، payment_event_id؛ فقط webhook امضاشده و idempotent |

در محصول سروری: session معتبر → RLS مالکیت → بررسی سهمیه و ساخت پروژه در تراکنش → دسترسی به پیام/گام. تصمیم اشتراک یا role از کلاینت پذیرفته نشود. کلید AI و service-role فقط در secret store سرور باشد. این مدل نیازمند migration و آزمون مستقل است؛ انتقال محلی به سرور خودکار نیست.

پیشنهاد نگهداری آینده: پس از درخواست حذف، قطع دسترسی فوری، حذف دادهٔ فعال تا ۳۰ روز و انقضای backup تا ۹۰ روز؛ این سیاست هنوز تصویب و اجرا نشده و تضمین عملیاتی این نسخه نیست.
